# Генетический алгоритм отбора признаков

Точка входа — `select_features_genetic()`. Алгоритм ищет подмножество признаков, на котором ваш `scorer` даёт минимальное значение на валидации. Модель в алгоритм не зашита: `scorer` — произвольный callable, который сам обучает нужную модель и возвращает `float`. Для CatBoost есть готовая фабрика `make_catboost_scorer`.

Статья устроена так: сначала быстрый старт и принцип работы, затем **словарь всех настроек** (что можно менять, что зашито в код, чего нет), отдельный раздел про **вероятности**, и в конце подводные камни и рецепты настройки.

---

## Быстрый старт

```python
from ml_toolkit.feature_selection import make_catboost_scorer, select_features_genetic

scorer = make_catboost_scorer(
    task='classification',
    metric='pr_auc',
    model_params={'iterations': 200, 'verbose': 0},
    cat_features=['region'],
)

selected = select_features_genetic(
    X_train, y_train, X_valid, y_valid,
    feature_names=list(X_train.columns),
    scorer=scorer,
    gen_params={
        'max_features': 30,
        'population_size': 20,
        'n_generations': 10,
        'cross_probability': 0.5,
        'mutation_probability': 0.2,
        'start_probability_to_include_feature': 0.03,
        'seed': 42,
    },
)
```

Возвращается список имён признаков из глобально лучшей особи за всю историю.

---

## Как это работает

Каждая **особь** — бинарный вектор длиной `N` (число кандидатов в `feature_names`): `1` — признак включён, `0` — выброшен. **Фитнес** особи — значение `scorer` на срезе `X[selected]` (плюс штраф за лишние признаки). Чем меньше, тем лучше.

```
создать популяцию из population_size особей          (инициализация)
for gen in 1..n_generations:
    offspring = копии pop
    для каждой пары:      с вероятностью cross_probability      → скрещивание
    для каждой особи:     с вероятностью mutation_probability   → мутация
    (после каждого оператора — ремонт: ограничение max_features, must_be_included)
    оценить особей без фитнеса (кэш по точной хромосоме)
    best_overall = лучшая особь за всю историю
    pop = [копия best_overall] + турнир(offspring, k = population_size - 1)
    проверить early stopping
вернуть признаки из best_overall
```

Что важно понимать:

- **Элитизм.** По умолчанию лучшая за всю историю особь переходит в следующее поколение (`elite_size = 1`). Остальные `population_size - elite_size` мест разыгрываются турниром **только среди потомков** (родители в турнире не участвуют).
- **Кэш.** Фитнес хранится по кортежу `tuple(chromosome)`: одна и та же комбинация признаков не оценивается дважды за один вызов.
- **Оценка последовательная.** Особи оцениваются по одной, без параллелизма на уровне GA. Параллелить можно только внутри `scorer` (например, `thread_count` у CatBoost).
- **Стоимость.** Верхняя оценка числа вызовов `scorer` — `population_size × n_generations`. Реальное число ниже: в каждом поколении заново оцениваются только изменённые особи, то есть примерно `population_size × (1 − (1 − cross_probability) × (1 − mutation_probability))`, минус попадания в кэш. Первое поколение оценивает всю популяцию целиком.

## Словарь настроек

Настройки делятся на четыре группы. Последние две важны, чтобы не искать в API то, чего там нет.

1. [Ключи `gen_params`](#ключи-gen_params) — настраиваются сразу.
2. [Через `scorer` и `generation_callback`](#настройки-через-scorer-и-callback) — вся «модельная» часть.
3. [Зашито в код](#зашито-в-код-не-настраивается) — значения есть, но менять их можно только правкой `_core.py`.
4. [Не реализовано](#не-реализовано-идеи) — то, что часто ожидают от генетического алгоритма, но в модуле нет.

### Ключи `gen_params`

Обязательные:

| Ключ | Тип | Что делает | Больше → | Меньше → |
|---|---|---|---|---|
| `max_features` | `int ≥ 1` | Жёсткий потолок числа признаков в особи. Лишние снимаются случайно (`repair`). | Шире поиск, дороже оценка, больше переобучения на валидацию | Меньше и проще модель, но ремонт чаще ломает найденные комбинации |
| `population_size` | `int ≥ 2` | Число особей в поколении. | Шире охват, стабильнее поиск; стоимость растёт линейно | Быстрее, но поиск «схлопывается» в одном решении |
| `n_generations` | `int ≥ 1` | Максимум поколений (без early stopping — ровно столько). | Дольше, глубже поиск | Быстрее, недоотбор |
| `cross_probability` | `float [0, 1]` | Вероятность скрещивания для каждой пары соседних особей. | Больше комбинирования родителей, быстрее сходимость | Меньше обмена, поиск идёт в основном за счёт мутации |
| `mutation_probability` | `float [0, 1]` | Вероятность того, что особь вообще мутирует. Дальше внутри неё каждый бит флипается с вероятностью `mutation_gene_probability` (по умолчанию `0.05`) — или так, чтобы в среднем получилось `mutation_flips` флипов. | Больше разнообразия; при больших `N` каждая мутация меняет десятки бит (см. [эксперимент](#мутация-и-размер-задачи)) | Меньше исследования, риск застрять |

Инициализация — **ровно один** из двух ключей (оба или ни одного → `ValueError`):

| Ключ | Тип | Что делает |
|---|---|---|
| `start_probability_to_include_feature` | `float` | Каждый бит стартовой особи включается независимо с этой вероятностью. Ожидаемое число включённых признаков — `N × p`. |
| `start_n_features` | `int` | В каждой стартовой особи ровно столько случайно выбранных признаков (без возврата, не больше `N`). |

Необязательные:

| Ключ | Тип, умолчание | Что делает |
|---|---|---|
| `n_features_without_penalty` | `int`, `0` | Сколько признаков «бесплатно». Не может превышать `max_features`. |
| `penalty_for_extra_feature` | `float`, `0.0` | Относительный штраф за каждый признак сверх бесплатных (формулы — [ниже](#функция-приспособленности-и-штраф)). |
| `min_improvement` | `float`, `0` | Early stopping: минимальное **абсолютное** улучшение лучшего фитнеса за окно. |
| `min_improvement_in_percents` | `float`, `0` | Early stopping: минимальное улучшение в **процентах** от значения лучшего фитнеса в начале окна. |
| `n_epoch_for_min_improvement` | `int`, `1` | Размер окна early stopping в поколениях. |
| `must_be_included` | `list[int \| str]`, `[]` | Обязательные признаки: целые — индексы в `feature_names`, строки — имена. Это **список**, строка не подойдёт (см. [подводные камни](#подводные-камни)). |
| `seed` | `int` | Фиксирует `random.seed` и `np.random.seed` (глобальное состояние!). |
| `mutation_gene_probability` | `float [0, 1]`, `0.05` | Вероятность флипа **каждого** гена внутри мутирующей особи (`indpb`). |
| `mutation_flips` | `float > 0` | То же через ожидаемое число флипов на одну мутирующую особь: `mutation_gene_probability = mutation_flips / N` (не больше 1). Удобнее, потому что не зависит от размера задачи. **Взаимоисключающий** с `mutation_gene_probability`. |
| `crossover_gene_probability` | `float [0, 1]`, `0.5` | Вероятность обмена каждого гена между двумя родителями при uniform crossover. |
| `tournament_size` | `int ≥ 1`, `3` | Размер турнира при отборе: побеждает лучший из `tournament_size` случайных потомков. Больше — жёстче давление отбора. |
| `elite_size` | `int [0, population_size)`, `1` | Сколько лучших особей за всю историю переходит в следующее поколение без изменений. `0` — без элитизма (лучшая особь всё равно возвращается в результате). |

Валидация при старте:

| Условие | Реакция |
|---|---|
| `feature_names` пуст | `ValueError` |
| `max_features < 1`, `population_size < 2`, `n_generations < 1` | `ValueError` |
| Заданы оба или ни одного ключа инициализации | `ValueError` |
| `n_features_without_penalty > max_features` | `ValueError` |
| `len(must_be_included) > max_features` | `ValueError` |
| Индекс в `must_be_included` вне `[0, N-1]` | `ValueError` |
| Имя в `must_be_included` отсутствует в `feature_names` | предупреждение в лог, признак пропускается |
| Неизвестный ключ в `gen_params` | `ValueError` со списком допустимых и подсказкой при опечатке |
| Заданы оба ключа: `mutation_gene_probability` и `mutation_flips` | `ValueError` |
| `mutation_gene_probability` или `crossover_gene_probability` вне `[0, 1]`, `mutation_flips ≤ 0` | `ValueError` |
| `tournament_size` не целое или `< 1`; `elite_size` не целое или вне `[0, population_size)` | `ValueError` |

### Настройки через `scorer` и callback

Всё, чего нет в `gen_params`, задаётся замыканием `scorer`. Его интерфейс:

```python
ScorerFn = Callable[[pd.DataFrame, pd.Series, pd.DataFrame, pd.Series], float]
score = scorer(X_train[selected], y_train, X_valid[selected], y_valid)
```

`scorer` возвращает **float для минимизации**: для метрик «выше — лучше» верните отрицательное значение.

| Что настраиваем | Как |
|---|---|
| Модель и её гиперпараметры | Любая: CatBoost, LightGBM, sklearn, XGBoost. Внутри `scorer` вы сами решаете, сколько итераций и какая регуляризация. Для скорости берите заведомо облегчённую модель |
| Метрика | Строка в `make_catboost_scorer` (список ниже) или произвольный `callable(y_true, y_score)` |
| Дополнительный штраф или бонус | Любая формула внутри `scorer`: аддитивный штраф за число признаков, цена отдельных признаков, штраф за нестабильность |
| Категориальные признаки | `cat_features` в `make_catboost_scorer`; фильтруются по колонкам среза автоматически |
| Бейзлайн (residual learning) | `baseline_train`, `baseline_valid` — предвычисленные массивы, а не имена колонок |
| Постобработка предсказаний (регрессия) | `postprocess_fn` |
| Воспроизводимость модели | `random_seed` в `model_params` (отдельно от `seed` GA) |
| Наблюдение за ходом поиска | `generation_callback(gen, best_score, mean_score, n_features_best)` |

Метрики `make_catboost_scorer`. Регрессия: `'mae'`, `'rmse'`, `'median_ae'`, `'mape'`, `'smape'`, `'r2'`. Классификация (общий реестр с `ml_toolkit.model_evaluation.CLASSIFICATION_PRESETS`): `'pr_auc'`, `'roc_auc'`, `'f1'`, `'precision'`, `'recall'`, `'balanced_accuracy'`, `'accuracy'`, `'mcc'`, `'cohen_kappa'`, `'gini'`, `'log_loss'` (алиас `'logloss'`), `'brier'`, `'ece'`. `'ks'` только для бинарной задачи.

Мультикласс определяется автоматически по числу уникальных меток в `y_train`; строковые метрики сами переключаются на macro- или OvR-агрегацию, а для callable-метрики приходит полная матрица `predict_proba` формы `(n, n_classes)`. Если `loss_function` в `model_params` не задан, для мультикласса ставится `'MultiClass'`.

Примеры `scorer` на других моделях:

```python
from lightgbm import LGBMClassifier
from sklearn.metrics import average_precision_score

def lgbm_scorer(X_tr, y_tr, X_va, y_va):
    model = LGBMClassifier(n_estimators=300, verbose=-1).fit(X_tr, y_tr)
    return -average_precision_score(y_va, model.predict_proba(X_va)[:, 1])
```

```python
def precision_at_k(k):
    def _metric(y_true, proba):
        top_k = np.argsort(proba)[-k:]
        return -float(y_true[top_k].mean())
    return _metric

scorer = make_catboost_scorer(task='classification', metric=precision_at_k(10), model_params={'verbose': 0})
```

### Зашито в код (не настраивается)

Вероятности обмена и флипа гена, размер турнира и размер элиты раньше были здесь, теперь они вынесены в `gen_params` (см. выше). Остальное регистрируется в `toolbox` внутри `select_features_genetic` (`_core.py`) и меняется только правкой кода:

| Что | Значение | Роль |
|---|---|---|
| Тип операторов | uniform crossover, flip-bit мутация | Другие операторы недоступны |
| Направление оптимизации | минимизация | `weights=(-1.0,)` |
| Ремонт лишних признаков | случайное удаление | Не учитывает фитнес и не смотрит на важность признаков |
| Ремонт пустой особи | один случайный признак | |
| Источник турнира | только `offspring` | Родители выживают лишь через элиту (`elite_size`) |
| Кэш фитнеса | по точной хромосоме | Не отключается |

### Не реализовано (идеи)

Этого в модуле **нет**. Список нужен, чтобы понимать границы, и как заготовка, если понадобится расширять API:

- Индивидуальные вероятности признаков: свой prior на включение при инициализации, свои веса мутации по признакам.
- Другие операторы скрещивания и мутации (одно- и двухточечное скрещивание, мутация с **точно** фиксированным числом флипов (сейчас `mutation_flips` задаёт лишь среднее), swap-мутация, мутация с bias «удалить чаще, чем добавить»).
- Ремонт с учётом качества (удалять наименее важные признаки, а не случайные).
- Адаптивные вероятности (рост мутации при стагнации, затухание по поколениям).
- Островная модель, нишевание, поддержание разнообразия популяции.
- Параллельная оценка особей.
- Многокритериальная оптимизация (качество и число признаков как отдельные цели вместо штрафа).
- Warm start: начать с ранее найденного набора, а не со случайной популяции.
- Кросс-валидация внутри фитнеса (можно реализовать самому внутри `scorer`).

## Вероятности: на что и как можно влиять

В алгоритме восемь вероятностных механизмов, и настраиваются они все.

| Механизм | Уровень | Значение | Настраивается |
|---|---|---|---|
| Включение признака при инициализации | ген | `start_probability_to_include_feature` | да |
| Число признаков при инициализации | особь | `start_n_features` | да |
| Скрещивание пары | пара особей | `cross_probability` | да |
| Мутация особи | особь | `mutation_probability` | да |
| Обмен гена при скрещивании | ген | `crossover_gene_probability` (`0.5`) | да |
| Флип гена при мутации | ген | `mutation_gene_probability` (`0.05`) или `mutation_flips` | да |
| Выбор в турнире | давление отбора | `tournament_size` (`3`) | да |
| Выживание лучших особей | элита | `elite_size` (`1`) | да |

### Полезные формулы

- Ожидаемое число включённых признаков на старте: `N × start_probability_to_include_feature`.
- Доля особей, изменённых за поколение: `1 − (1 − cross_probability) × (1 − mutation_probability)`. Только они переоцениваются, поэтому это же оценка стоимости поколения.
- Число флипов при мутации одной особи: в среднем `mutation_gene_probability × N` (при `mutation_flips` это ровно заданное число), из них добавлений `≈ mutation_gene_probability × (N − k)` и удалений `≈ mutation_gene_probability × k`, где `k` — число включённых признаков.
- Вероятность флипа конкретного гена в поколении за счёт мутации: `mutation_probability × mutation_gene_probability`.
- Давление отбора: лучший потомок попадает в очередной турнир примерно с вероятностью `tournament_size / population_size`.

### Мутация и размер задачи

Вероятность флипа гена по умолчанию `0.05` и не зависит от `N`, а решения обычно разреженные (`k ≪ N`). Поэтому чем больше кандидатов, тем больше **новых** признаков мутация добавляет в решение, а затем ремонт **случайно** снимает лишние до `max_features`. Результат — мутация разрушает найденную комбинацию.

Измерение на реальных функциях модуля (`mut_flip_bit_with_repair`, значение по умолчанию `0.05`, `k = max_features = 30`): доля признаков родителя, оставшихся после **одной** мутации.

| Число кандидатов `N` | Добавляется новых бит до ремонта | Сохраняется признаков родителя |
|---|---|---|
| 50 | ≈ 1 | 94% |
| 100 | ≈ 4 | 89% |
| 300 | ≈ 14 | 68% |
| 1000 | ≈ 48 | 37% |
| 3000 | ≈ 148 | 16% |

Напрашивается вывод «раз мутация разрушает решение, мутировать надо реже». **Проверка его не подтвердила.** Эксперимент: синтетическая линейная задача, `N = 1000`, 10 полезных признаков, `Ridge` в качестве `scorer`, `max_features = 20`, популяция 30, 30 поколений, 16 сидов (среднее ± стандартная ошибка). Эксперимент ставился до того, как параметры были вынесены в `gen_params`: значения подменялись в памяти. `indpb = 2/N` соответствует `mutation_flips=2`. Тестовая MSE считается на отдельной выборке, «найдено полезных» — доля из 10 истинных признаков в результате.

| Конфигурация | Флипов на мутацию | Val MSE | Test MSE | Найдено полезных |
|---|---|---|---|---|
| Как сейчас (`indpb = 0.05`, `mutation_probability = 0.2`) | ≈ 50 | 6.44 ± 0.39 | 6.78 ± 0.43 | 38% ± 2% |
| Реже мутировать (`mutation_probability = 0.05`) | ≈ 50 | 7.08 ± 0.30 | 7.85 ± 0.44 | 31% ± 3% |
| `indpb = 1/N`, `mutation_probability = 0.9` | ≈ 1 | 4.58 ± 0.44 | 4.89 ± 0.51 | 56% ± 4% |
| `indpb = 2/N`, `mutation_probability = 0.9` | ≈ 2 | 3.93 ± 0.37 | 4.23 ± 0.43 | 62% ± 3% |
| `indpb = 4/N`, `mutation_probability = 0.9` | ≈ 4 | 3.74 ± 0.27 | 3.93 ± 0.29 | 62% ± 2% |
| `indpb = 2/N`, `mutation_probability = 0.9`, турнир 6 | ≈ 2 | 4.47 ± 0.27 | 4.74 ± 0.32 | 58% ± 2% |

Как это читать:

- **Снижение `mutation_probability` не помогло**: найдено даже меньше полезных признаков.
- **Помогает другое: мало флипов внутри мутирующей особи** (1–4 вместо ≈ 50) при высокой доле мутирующих. Тестовая MSE падает с 6.8 до 3.9–4.9, находится 56–62% полезных признаков против 38%. Это настраивается через `mutation_flips` (или `mutation_gene_probability`).
- **Размер турнира** в плюс не дал: 6 вместо 3 в пределах шума хуже.
- Оговорки: одна синтетическая линейная задача и один быстрый `scorer`. Направление логично из механики (малые шаги вокруг найденного решения), но масштаб эффекта на ваших данных может быть другим. Даже лучшие конфигурации далеки от идеала (на истинном наборе val MSE ≈ 0.9): при `N = 1000` и около тысячи оценок поиск остаётся слабым.

**Что делать.** На большом `N` задайте `mutation_flips` в пределах 2–4 и высокий `mutation_probability` (около 0.9) — это конфигурации из таблицы, давшие лучший результат. Для вашей задачи это отправная точка, а не гарантия: проверьте на своих данных. Дополнительно полезно **сократить пул кандидатов до запуска GA** (`FeatureScreener` из `ml_toolkit.feature_selection`), например до нескольких сотен признаков. Понижать `mutation_probability` при большом `N` не нужно: само по себе это не помогало.

```python
gen_params = {
    'max_features': 20, 'population_size': 30, 'n_generations': 30,
    'cross_probability': 0.6,
    'mutation_probability': 0.9,
    'mutation_flips': 3,          # ≈ 3 флипа на мутацию независимо от N
    'start_probability_to_include_feature': 0.015,
}
```

### Как воздействовать на вероятности сегодня

**1. Старт.** Выбирайте `start_probability_to_include_feature ≈ max_features / N`, максимум до `1.0 × max_features / N`. Если `N × p > max_features`, ремонт при инициализации случайно срежет признаки, и стартовая популяция будет случайной. Например, `p = 0.1` при `N = 1000` даёт около 100 признаков в особи против `max_features = 30`. Альтернатива — `start_n_features`: он задаёт размер прямо.

**2. Скрещивание.** `cross_probability` в диапазоне 0.5–0.9 — типичный выбор. Скрещивание разреженных родителей размер потомка сохраняет (каждый родитель отдаёт примерно половину своих единиц), поэтому оно безопаснее мутации.

**3. Мутация.** Два рычага: `mutation_probability` (какая доля особей мутирует) и `mutation_flips` / `mutation_gene_probability` (насколько сильно). Второй важнее: на больших `N` снижение `mutation_probability` не помогало, а уменьшение числа флипов — помогало (см. эксперимент выше). При `mutation_flips` число флипов не зависит от `N`.

**4. Приоритеты признаков.** Есть два «крайних» значения вероятности:
- вероятность 1 — `must_be_included`: признак всегда в особи;
- вероятность 0 — исключить признак из `feature_names`.

Промежуточных значений («этот признак вероятнее полезен, чем тот») **нет**: все кандидаты равноправны. Обходные пути: заранее сократить пул до сильных кандидатов, запускать GA в два этапа (сначала по группе, затем по объединению победителей) или встроить предпочтения в `scorer` через штраф за конкретные признаки.

**5. Давление отбора.** `tournament_size` (по умолчанию 3): больше — жёстче отбор, быстрее сходимость и выше риск застрять. В нашем эксперименте увеличение до 6 не помогло, поэтому крутить его стоит только при явной проблеме. Косвенно давление задают `population_size` и `elite_size`.

**6. Размер решения.** Влиять на число признаков в результате можно `max_features` (жёстко) и штрафом (мягко). Штраф пропорционален качеству, а не фиксирован, см. следующий раздел.

Если этих рычагов не хватает, следующее по полезности расширение — `start_probabilities` (вектор или словарь prior'ов по признакам, например из скрининга). Его в модуле пока нет, это эскиз.

## Функция приспособленности и штраф

1. Из хромосомы берутся имена признаков `selected`. Число признаков должно быть в `[1, max_features]`.
2. Вызывается `score = scorer(X_train[selected], y_train, X_valid[selected], y_valid)`.
3. Добавляется штраф за признаки сверх бесплатных:

```
extra = max(0, n_selected - n_features_without_penalty)
score >= 0:  score *= (1 + extra * penalty_for_extra_feature)
score <  0:  score *= (1 - extra * penalty_for_extra_feature)
```

Знак `score` определяет направление: и для «меньше — лучше» (`score > 0`), и для отрицательной «выше — лучше» метрики (`score < 0`) штраф ухудшает результат.

**Цена признака относительна.** Каждый лишний признак стоит `penalty × |score|`. Пример: `score = −0.30` (это `−PR-AUC`), `penalty = 0.005`, `n_features_without_penalty = 20`, выбрано 35 признаков. Тогда `extra = 15`, множитель `1 − 15 × 0.005 = 0.925`, фитнес `−0.2775`. То есть 15 лишних признаков должны прибавить не менее 7.5% относительного качества, чтобы окупиться. Для метрики со значением `100` (например, MAE) те же 15 признаков дают `100 × 1.075 = 107.5`.

**Ограничения штрафа.** Он мультипликативный: при `score` около нуля почти не действует, а при `extra × penalty ≥ 1` для отрицательных метрик множитель обнуляется и меняет знак. Если нужен фиксированный штраф на признак, добавьте его в `scorer`, а `penalty_for_extra_feature` оставьте `0`.

## Ремонт и ограничения

Функция `repair_individual` вызывается после инициализации, скрещивания и мутации и гарантирует валидность:

1. Признаки из `must_be_included` выставляются в `1`.
2. Если не выбрано ни одного признака, добавляется один случайный.
3. Если выбрано больше `max_features`, случайно снимаются лишние, кроме обязательных.

Ремонт работает **случайно и не смотрит на качество**. Отсюда важность согласовывать `start_*`, `mutation_probability` и `max_features`: чем чаще ремонт срабатывает, тем меньше от эволюции остаётся.

## Early stopping

Каждое поколение сравнивается лучший фитнес сейчас и `n_epoch_for_min_improvement` поколений назад: `improvement = best[-(1 + n)] − best[-1]` (для минимизации улучшение положительно). Ожидаемое улучшение:

- `min_improvement` — абсолютное число;
- `min_improvement_in_percents` — процент от `|best[-(1 + n)]|`.

Если фактическое улучшение меньше ожидаемого, цикл останавливается. Проверка начинается, когда накопилось `1 + n` значений истории. Без обоих ключей алгоритм отрабатывает все `n_generations`.

Заданы оба ключа сразу: код **не выдаёт ошибку**, побеждает `min_improvement` (процентный ключ игнорируется).

## Наблюдение за поиском

`generation_callback(gen, best_score, mean_score, n_features_best)` вызывается в конце каждого поколения. `best_score` и `mean_score` — сырые значения фитнеса (для «выше — лучше» метрик они отрицательные).

```python
history = []
select_features_genetic(
    ..., generation_callback=lambda g, best, mean, k: history.append((g, best, mean, k)),
)

import pandas as pd
pd.DataFrame(history, columns=['gen', 'best', 'mean', 'n_features']).plot(x='gen', y=['best', 'mean'])
```

Что смотреть: если `mean` почти совпадает с `best` — популяция схлопнулась (нужны больше `population_size` или мутация); если `mean` сильно хуже и не приближается к `best` — слишком много мутации или ремонта.

## Подводные камни

Ниже — то, что проверялось запуском на текущей версии кода.

- **`must_be_included` — только список.** Строка `'baseline'` обходится по символам: каждая буква не находится в `feature_names`, выдаются предупреждения, а признак **не закрепляется**. Всегда передавайте `['baseline']`.
- **Обязательные признаки в стартовой популяции.** Раньше ремонт при инициализации вызывался без `must` и мог снять обязательный признак, если `N × start_probability > max_features`: на проверке обязательных признаков не было у 118 из 120 оценённых особей. Исправлено, теперь `must` защищён и при инициализации. Держать `N × start_probability ≤ max_features` всё равно стоит, иначе стартовая популяция сильно обрезается случайно.
- **Неизвестные ключи `gen_params` теперь дают `ValueError`.** Опечатка в необязательном ключе (например, `penalty_for_extra_featur`) раньше молча игнорировалась; сообщение содержит подсказку с похожим именем. Это поведение изменилось: лишние ключи, которые кто-то передавал «на всякий случай», теперь вызовут ошибку.
- **Оба ключа early stopping принимаются молча.** Документация раньше говорила «не допускаются», на деле побеждает `min_improvement`.
- **Переобучение на валидацию.** Алгоритм выбирает признаки по валидации и прогоняет по ней сотни моделей: итоговое значение метрики оптимистично. Оценивайте выбранный набор на отдельной выборке (лучше более позднем периоде), не использовавшейся ни в GA, ни в early stopping внутри `scorer`.
- **Глобальное состояние `seed`.** `seed` вызывает `random.seed` и `np.random.seed`, то есть влияет на остальной код процесса. При этом воспроизводимость требует и детерминированного `scorer` (фиксируйте `random_seed` и по возможности `thread_count`).
- **Ремонт случаен.** См. раздел про мутацию: при больших `N` это главная причина слабой сходимости.
- **Стоимость.** Один вызов GA — это до `population_size × n_generations` обучений модели. Планируйте бюджет и берите облегчённую модель внутри `scorer`.

## Рецепты настройки

| Ситуация | Что делать |
|---|---|
| Очень много признаков (`N` в тысячах) | `mutation_flips` 2–4 при `mutation_probability` около 0.9; `start_probability ≈ max_features / N`; по возможности сначала `FeatureScreener` до нескольких сотен |
| Нужен небольшой понятный набор | Ниже `max_features`, `n_features_without_penalty` равен целевому размеру, `penalty_for_extra_feature` 0.005–0.01 |
| Поиск быстро схлопывается | Больше `population_size`, чуть выше `mutation_probability`, ниже `cross_probability` |
| Поиск блуждает и не сходится | Меньше флипов на мутацию (`mutation_flips` 2–4), проверьте, что ремонт не срабатывает на старте (`N × start_probability ≤ max_features`), выше `cross_probability`. Просто снизить `mutation_probability` при большом `N` в тестах не помогало |
| Ограниченный бюджет | `n_generations` небольшое + early stopping (`n_epoch_for_min_improvement = 2`), лёгкая модель в `scorer` |
| Нужен обязательный признак (бейзлайн) | `must_be_included=['имя']` (список!), затем проверьте результат |
| Метрика в процентах или очень мала | Штраф мультипликативный, при близком к нулю фитнесе он почти не работает: используйте аддитивный штраф внутри `scorer` |
